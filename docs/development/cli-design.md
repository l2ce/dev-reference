# Проект целевого CLI

**Статус: предложение нового интерфейса. Команды и параметры ниже не являются
описанием текущей реализации.**

Документ проектирует CLI с нуля вокруг работы исследовательского агента и человека,
наблюдающего за его действиями. Совместимость с существующими командами не определяет
целевой дизайн. Предметные понятия берутся из [модели базы](../architecture/domain-model.md);
этот проект не меняет действующий SQL-контракт и не разрешает наполнение базы примерами.

`l2ref` — условное имя исполняемого файла в примерах, а не решение о названии пакета.
Названия, номера и даты в примерах иллюстрируют интерфейс, не подтверждают исторические факты.

## 1. Что должен обеспечивать CLI

Агент должен без прямого доступа к SQLite и вспомогательного кода уметь:

1. Понять структуру и состояние базы, доступные типы, поля и операции.
2. Найти записи, получить только заголовки и краткие описания либо полные документы.
3. Прочитать исходные данные для редактирования, включая все языки и связи.
4. Создать связанную цепочку записей, не назначая UUID и не дублируя адреса в JSON.
5. Изменить один текст, перевод, источник, вопрос или связь, сохранив остальное.
6. Увидеть содержательный результат операции до её применения.
7. Исправить ошибку по сообщению CLI, не исследуя код валидатора.
8. Массово прочитать или изменить выбранные записи без ручного обхода страниц.

**Текст — основной интерфейс.** Он должен быть удобен и агенту, и пользователю.
JSON — системное представление для интеграций, диагностики и скриптов, а не
обязательное условие выполнения обычной работы.

Обычные операции создания, изменения, удаления, перевода и связывания выполняются
флагами и текстом, в том числе многострочным, переданным прямо в команду или stdin.
Чтение из существующего файла — дополнительный вариант. Создавать временные файлы
только ради передачи текста в CLI не требуется. Структурированный ввод допустим
для сложных данных и батчинга, но не должен становиться единственным способом
повседневного редактирования.

## 2. Базовые решения

### 2.1. Один адрес — одна запись

| Адрес                           | Что адресует                             |
| ------------------------------- | ---------------------------------------- |
| `branch:main`                   | Ветку                                    |
| `saga:the-chaotic-throne`       | Сагу                                     |
| `chronicle:the-kamael`          | Хронику-группу                           |
| `release:the-kamael`            | Самостоятельный релиз                    |
| `region:na`                     | Регион, не выход конкретного релиза      |
| `country:us`                    | Страну                                   |
| `release-context:the-kamael:na` | Региональный контекст конкретного релиза |
| `protocol:152`                  | Протокол                                 |
| `packet:key-packet`             | Карточку знания                          |
| `packet:key-packet:rev-1`       | Конкретную техническую редакцию          |

Для сценариев и статей действуют пространства `scenario:` и `article:` с тем же
различением карточки и редакции.

- В позиционных аргументах используются полные адреса. По префиксу CLI сам определяет тип.
- В однозначно типизированных флагах допустим короткий код: `--region na` равнозначен
  `--region region:na`. Это нормализация, а не поиск по названию.
- Название, текущий язык и родительская группировка не определяют идентичность записи.
- UUID назначаются автоматически и не требуются для обычных действий.
- Код не меняется обычным `update`. Перегруппировка релиза не меняет его адрес.
- Никаких специальных релизов `base`, искусственных частей и фиктивных регионов.
- Неизвестность сохраняется явно. CLI не выводит регион, дату или протокол из соседней записи.

### 2.2. Единая грамматика, без отдельных CRUD-команд для каждого типа

```text
l2ref <операция> [адреса...] [параметры]
```

Чтение релиза, региона и статьи начинается с одной операции `read`. Агенту не нужно
сначала преобразовывать префикс адреса в имя командной группы.

Предметные подкоманды используются там, где операция действительно особая:
`translation`, `revision`, `source`, `question`, `locale`.

### 2.3. Имя поля обозначает смысл, а не формат

| Поле CLI      | Назначение                                |
| ------------- | ----------------------------------------- |
| `title`       | Заголовок                                 |
| `summary`     | Краткое описание / аннотация              |
| `description` | Основное описание или полный текст записи |

`summary` не вычисляется автоматически из начала `description`. Подготовленная аннотация
и полный документ — разные сведения.

Markdown — формат содержимого, указанный в схеме поля отдельно от его имени.
Если у записи появится второе самостоятельное текстовое поле, оно получит смысловое
имя, например `notes`, а не `markdown2`. Этот пример не добавляет поле `notes` в
предметную модель. Несколько полей могут иметь формат Markdown независимо друг от друга.

Имена публичных полей CLI стабильны. Текст, формат и правила редактирования описывает
схема; агенту не нужно изучать SQL или внутренние DTO.
Для каждого поля схема отдельно указывает смысл, тип, формат содержимого, область
владения — общая запись или перевод — и допустимость чтения из файла. Формат Markdown
сам по себе не определяет ни имя поля, ни его языковую принадлежность.

Языковые поля публичного ввода: `title`, `summary`, `description`, `translationStatus`,
`sources`, `questions`. Они относятся к явно выбранному языку. Одиночные предметные
связи называются `branch`, `saga`, `chronicle`, `release`, `region`, множественные —
`protocols`, `countries`. `name`, `server`, `direction`, `opcode`, `states`,
`servers`, `loginRevisions`, `status`, `order`, `releasedOn` сохраняют технический смысл.
Их доступность и тип определяются схемой конкретной операции, а не универсальным
объектом с произвольными свойствами.

## 3. Быстрый старт для агента

```bash
# Понять, что доступно и чем заполнена база.
l2ref help
l2ref types
l2ref status
l2ref stats --by type

# Найти нужное и прочитать только необходимый объём.
l2ref list --type releases --chronicle chronicle:gracia
l2ref find "Gracia" --type chronicles,releases
l2ref read release:gracia-part-1 --view brief
l2ref read release:gracia-part-1 --view full

# Передать многострочный текст прямо в команду и проверить изменение.
l2ref update release:gracia-part-1 --locale ru --description='# Описание релиза

Первый абзац.

- Первый пункт
- Второй пункт' --dry-run

# Если черновик уже существует, его тоже можно использовать.
l2ref update release:gracia-part-1 --locale ru --set-file description=./draft.md --dry-run

# Связать записи без чтения и перезаписи всего списка связей.
l2ref link release-context:gracia-part-1:na protocols protocol:152 --dry-run

# Проверить результат и явно экспортировать снимок для Git.
l2ref read release:gracia-part-1 --view full
l2ref validate
l2ref export
```

## 4. Общие параметры

| Параметр                      | Контракт                                                                             |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| `--database <path>`           | Явно выбрать SQLite; по умолчанию рабочая база проекта                               |
| `--locale <code>`             | Язык данных; по умолчанию основной язык базы                                         |
| `--format text\|json`         | Текст по умолчанию; JSON — системный вывод                                           |
| `--view <view>`               | Объём чтения записи: `brief`, `full`, `edit`                                         |
| `--content <field>`           | Прочитать только буквальное содержимое одного текстового поля                        |
| `--set-stdin <field>`         | Записать текст одного поля из stdin без промежуточного файла                         |
| `--set-file <field=path>`     | Записать текст разрешённого поля из UTF-8 файла или stdin                            |
| `--fields <names>`            | Явно выбрать поля вместо набора по умолчанию                                         |
| `--all-locales`               | Явно запросить все языки там, где операция это поддерживает                          |
| `--with-version`              | Дополнительно показать полный токен версии снимка для последующей записи             |
| `--if-version <token>`        | Применить изменение только к ожидаемой версии снимка                                 |
| `--dry-run`                   | Рассчитать и проверить изменение без записи                                          |
| `--diff summary\|full`        | Объём изменений: `full` по умолчанию для предпросмотра, `summary` для обычной записи |
| `--input <path\|->`           | Структурированный ввод из файла или stdin как альтернатива обычным флагам            |
| `--color auto\|always\|never` | Только оформление; `auto` не использует цвет вне TTY                                 |
| `--verbose`                   | Дополнительные служебные подробности; не расширяет предметную область                |
| `--help`                      | Контекстная справка без открытия базы, если данные для неё не нужны                  |

Параметры допустимы только там, где имеют смысл. Неподдерживаемый фильтр или поле —
ошибка с объяснением, а не молча проигнорированное условие.

В сокращённых сигнатурах ниже не повторяются все общие параметры. Каждая предметная
мутация, включая вложенные операции, поддерживает `--dry-run` и `--if-version`.
`--input` использует схему той же операции и не требует внутренних оболочек базы.

Дополнительные правила:

- `--locale` меняет язык данных, а не язык интерфейса CLI.
- `--locale` и `--all-locales` не могут одновременно задавать область одной операции.
- Нет скрытого выбранного протокола, языка или записи из предыдущего процесса CLI.
- Команды чтения открывают базу только для чтения и не создают отсутствующий SQLite-файл.
- Нет обязательного интерактивного редактора, pager или подтверждения, ожидающего stdin.
- Чтение и запись через stdin не зависят от наличия TTY; `-` всегда означает stdin.
- Если две опции пытаются прочитать stdin, CLI отклоняет команду до начала чтения.
- Относительные пути обычной команды отсчитываются от текущего каталога.
- Источники, даты и статусы не заполняются автоматически ради прохождения проверки.

## 5. Чтение: от короткой карточки до полного исходного документа

### 5.1. Представления и чтение содержимого поля

| Представление       | Содержимое                                                                                                |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `brief`             | Адрес, заголовок, краткое описание, существенный контекст и короткие состояния                            |
| `full`              | Полный текст выбранного языка, предметные поля, адреса связей, источники и открытые вопросы               |
| `edit`              | Полное нормализованное содержимое записи для редактирования, все языки, собственные UUID и исходные связи |
| `--content <field>` | Отдельный режим чтения только буквального содержимого выбранного текстового поля                          |

- `list` и `find` по умолчанию используют `brief`.
- `read` по умолчанию использует `full`.
- `full` показывает все поля выбранной записи и перевода, но не разворачивает рекурсивно
  полные тела связанных записей. Для обхода связей есть `relations` и `tree`.
- `--all-locales` расширяет `brief`/`full` до всех существующих переводов, а не подставляет один язык вместо другого.
- В поиске и фильтрах `--all-locales` проверяет существующие переводы и показывает,
  в каких языках есть совпадения. Одна предметная запись не превращается в несколько
  разных записей только из-за языков; языковые условия одного совпадения проверяются в одном переводе.
- `edit` всегда содержит все сохранённые переводы; ограничение его одним языком не допускается.
- Если задан `--fields`, выводятся выбранные поля; адрес записи остаётся видимым, кроме режима `--content`.
- Текст не обрезается молча. Сокращение достигается выбором представления, полей и записей.
- `full` и `edit` возвращают исходные текстовые поля с маркерами, не раскрывают `include`
  и не меняют авторские пробелы. Каждое поле с Markdown показано отдельно под своим именем.
- `--content description` требует одну запись, один язык и одну техническую редакцию,
  если она нужна. Допустимо выбрать любое текстовое поле, разрешённое схемой, независимо
  от его формата. В текстовом режиме stdout содержит только исходное содержимое:
  без заголовка CLI, отступов, хеша и заключительного сообщения.
- `--content` несовместим с `--view`, `--fields` и `--all-locales`.
  Явно запрошенный `--with-version` выводит токен в stderr и не меняет содержимое в stdout.
- В системном JSON режим `--content` возвращает `key`, `locale`, `field`, `content`
  и служебную оболочку; переносы и символы экранируются только правилами JSON.

### 5.2. `read`

```text
l2ref read <key...> [--view ...] [--locale ... | --all-locales]
                   [--protocol <key>] [--fields ...] [--with-version]
                   [--limit <n>] [--after <cursor>]
l2ref read --keys-file <path|-> [те же параметры]
l2ref read --selection <path> [те же параметры]
l2ref read <key> --content <field> [--locale ...] [--protocol ...] [--with-version]
```

`--keys-file` принимает UTF-8 файл с одним полным адресом на строку. Пустые строки
допускаются; адреса не интерпретируются как команды или шаблоны.

Перечисленные адреса читаются одним запросом, а не отдельным процессом для каждого
пакета. Без параметров пагинации возвращается весь явно запрошенный набор:
у `read` нет скрытого ограничения на 20 или 50 адресов. Для чтения порциями можно
явно задать `--limit` и продолжать через `--after`; курсор учитывает порядок адресов,
контекст протокола, язык, представление и версию снимка.

Правила выбора технических знаний:

- Каталоговым адресам — веткам, сагам, хроникам, релизам, регионам и странам — протокол не нужен.
- Для `read packet:key-packet --protocol protocol:152` выбирается только применимая редакция.
- `read packet:key-packet:rev-1` читает явно указанную редакцию без угадывания применимости.
- `read packet:key-packet --view edit` читает саму карточку и краткий перечень её редакций;
  для полного текста редакции нужно указать её адрес.
- `brief` карточки без протокола показывает её собственное имя или код и перечень
  доступных редакций. Общий заголовок и описание не берутся из произвольно выбранной редакции.
- Если в смешанном запросе есть знания, требующие протокола, `--protocol` относится только к ним.
  Он не сужает чтение явно запрошенных каталоговых адресов.
- `protocol:152` и `protocol:273` в списке позиционных адресов — две записи для чтения,
  а не два неявных контекста для остальных сущностей. CLI не выбирает первый из них
  как контекст пакета и не создаёт автоматически комбинации «каждый пакет × каждый протокол».
- Текст другой редакции или языка не подставляется автоматически.
- Отсутствующая запись, отсутствующая применимость и отсутствующий перевод различаются
  и в тексте, и в JSON. Чтение нескольких адресов сохраняет порядок запроса.

```bash
l2ref read chronicle:the-kamael release:the-kamael region:na --view brief
l2ref read packet:key-packet --protocol protocol:152 --view full
l2ref read packet:key-packet:rev-1 --view edit
l2ref read release:gracia-part-1 --locale ru --content description > ./draft.md
```

#### Смешанный набор сущностей одним вызовом

```bash
l2ref read chronicle:gracia protocol:152 protocol:273 \
  release:gracia-part-1 region:na --view full
```

Команда читает пять разных записей одного согласованного снимка. Не требуются
отдельные вызовы для хроник, протоколов и регионов, общий протокол или JSON.
`--view brief` у того же запроса оставляет короткие карточки вместо полных описаний.

Каждая сущность имеет отдельный текстовый блок с номером, типом, адресом и названием:
сначала хроника, затем два протокола, релиз и регион — в порядке аргументов.
У каждого типа показаны его собственные поля; вывод не превращается в универсальную
таблицу с десятками неприменимых столбцов. Сведения о снимке и запросе общие, а не
повторяются в каждом блоке. Валидный, но отсутствующий адрес отмечается в своём блоке;
найденные записи не пропадают из результата.

Если в набор добавляется логическая карточка пакета, её контекст указывается явно:

```bash
l2ref read chronicle:gracia protocol:152 protocol:273 packet:key-packet \
  --protocol protocol:152 --view full
```

Оба протокола по-прежнему читаются как самостоятельные записи, а для пакета выбирается
редакция только под `protocol:152`. Явно адресованные редакции, например
`packet:key-packet:rev-1`, можно смешивать с каталоговыми сущностями и без выбора протокола.

### 5.3. `list`

```text
l2ref list [--type <types>] [фильтры] [--view brief|full|edit]
           [--fields ...] [--limit <n>] [--offset <n> | --after <cursor>]
           [--all] [--sort <fields>] [--save-selection <path>]
```

- Без `--type` перечисляются все предметные типы; область явно указана в заголовке.
- `--type` принимает зарегистрированные имена типов, например `releases,protocols`.
- Параметры списка одинаковы для всех типов; доступность конкретного фильтра описывает схема.
- По умолчанию возвращаются первые 20 записей и явно показываются общее число,
  границы страницы и команда продолжения с сохранёнными фильтрами.
- `--all` возвращает весь результат, а не первые 100 или 1000 строк. Он несовместим
  с ограничивающими страницу параметрами и не снимает фильтры.
- Курсор связан с запросом, сортировкой и версией снимка. Изменившаяся база не должна
  незаметно приводить к пропускам или повторениям при продолжении.
- `--offset` оставлен для понятного перехода к странице; для согласованного обхода
  изменяемой базы предпочтителен курсор или сохранённая выборка.
- У сортировки всегда есть устойчивый дополнительный критерий — полный адрес.
- `--save-selection` сохраняет точные адреса и версию снимка для последующих операций.
  В stdout остаётся обычный текстовый результат, а не содержимое служебного файла.
- Выборка содержит только записи, действительно возвращённые этим вызовом, а не все
  совпадения запроса за пределами страницы. Вывод явно сообщает её объём: например,
  «сохранены 50 показанных записей из 180». Для фиксации всего результата нужен `--all`.

```bash
l2ref list --type releases --chronicle chronicle:gracia
l2ref list --type releases --fields title,summary --all
l2ref list --type protocols --view edit --all
l2ref list --type release-contexts --region region:na --sort releasedOn,key
```

`list --view edit --all --format json` предоставляет полный предметный набор для
скриптов: без чтения физических таблиц и сборки тысяч файлов экспорта.
При выборе всех типов результат включает метаданные и реестр языков снимка.

### 5.4. `find`

```text
l2ref find <text> [--type <types>] [--search-in <fields>]
                 [--match contains|exact|prefix] [фильтры]
                 [параметры представления и пагинации list]
```

- Поиск работает по всему каталогу и знаниям, а не только по одному выбранному протоколу.
- По умолчанию ищет в `key` и текстовых полях, отмеченных схемой как поисковые,
  включая `title`, `summary`, `description` выбранного языка. Фактический набор
  полей показан в справке и метаданных; он не определяется словом Markdown в имени.
- `--search-in` явно расширяет или сужает поля, например до `sources.url` или `questions`.
- Без `--protocol` редакции знаний возвращаются под собственными адресами `...:rev-N`.
  Это поиск по исходным записям, не заявление о применимости к произвольному протоколу.
- С `--protocol` поиск знаний ограничен реально применимыми редакциями.
- Результат показывает поле совпадения и короткий фрагмент. Полный документ читается отдельно.
- Текстовый поиск нормализует Unicode и регистр; точность сравнения адресов и URL
  определяется их отдельными контрактами, а не неявным полнотекстовым преобразованием.

```bash
l2ref find "шифрование" --type articles,packet-revisions
l2ref find "Gracia" --type chronicles,releases
l2ref find "example.invalid" --search-in sources.url --all
```

### 5.5. Фильтры и признаки отсутствия

Общие фильтры чтения:

| Параметры                                        | Область                                                     |
| ------------------------------------------------ | ----------------------------------------------------------- |
| `--branch`, `--saga`, `--chronicle`, `--release` | Явная классификация и связанные с ней записи                |
| `--region`, `--country`                          | Явные региональные контексты, без вывода стран из региона   |
| `--protocol`, `--server`, `--direction`          | Техническая применимость и канал обмена                     |
| `--status`, `--translation-status`               | Полнота знания и состояние выбранного перевода              |
| `--has <field>`, `--missing <field>`             | Наличие / отсутствие значения, текста, связи или источников |
| `--source-url <url>`, `--source-host <host>`     | Точный URL источника / точное имя хоста                     |

Для `--has` и `--missing` схема перечисляет допустимые поля и их смысл. Например,
пустой Markdown и отсутствующий перевод — разные условия. Значение `0` не считается
отсутствующим; дата `null` не заменяется пустой строкой. `--source-host` не включает
поддомены без явно заданного отдельного условия.

Все фильтры применяются до пагинации. Для смешанных типов неподходящий фильтр
вызывает объяснимую ошибку: CLI не должен незаметно возвращать более широкую выборку.
Если `--type` не задан, предметный фильтр может определить естественную область:
например, `--server` выбирает типы знаний, имеющие канальную применимость. Такой набор
типов явно показан в заголовке и метаданных ответа. Для явно заданного несовместимого
типа фильтр всегда является ошибкой; он не пропускается и не исключает тип молча.

### 5.6. Общий контракт пагинации

Пагинация одинакова по смыслу для `list`, `find` и множественного `read`, включая
смешанные сущности. Единица страницы — целая запись в выбранном представлении,
а не строка, поле, язык или фрагмент Markdown.

- `--limit 10` означает максимум десять целых записей. Описание десятой записи
  не обрывается из-за того, что оно длиннее соседних.
- Для `read` по адресам страницы соответствуют позициям исходного запроса.
  Отсутствующий адрес сохраняет свою позицию и получает отдельный блок результата.
- Нумерация сквозная: после записей `1–10` идут `11–20`, а не новый набор `1–10`.
  Типы не перегруппировываются между страницами.
- Заголовок страницы содержит операцию, представление, язык, существенный контекст
  протокола и диапазон записей относительно всего набора.
- Завершение страницы содержит количество показанных записей, общее число,
  количество оставшихся и полную команду продолжения. На последней странице явно
  написано «Конец выборки», а не просто отсутствует строка курсора.
- Команда продолжения сохраняет адреса или ссылку на исходную выборку, фильтры,
  порядок, язык, представление и контекст. Пользователь не должен собирать её вручную
  по указанию «повторите те же параметры».
- Продолжение не зависит от уже прочитанного stdin: CLI подставляет исходные адреса
  либо явный неизменённый файл выборки, а не предлагает повторить `--keys-file -`
  без доступного исходного ввода.
- Курсор фиксирует позицию, запрос и версию снимка. Его нельзя незаметно использовать
  с другими адресами, фильтрами, языком или протоколом. Изменение базы приводит к
  объяснимому конфликту до выдачи новой страницы, а не к пропускам или дубликатам.
- Размер следующей порции можно явно уменьшить, сохраняя зафиксированную позицию
  и остальные условия. Это не меняет исходный набор.
- `--all` снимает разбиение результата на страницы, но не границы отдельных записей.
  Заголовок и завершение всего вывода сохраняются.
- В начале, между записями и в конце используются явные текстовые разделители,
  описанные в разделе 13.4. Одна пустая строка не считается надёжной границей документов.

Чтение без служебного оформления через `--content` — отдельный однозаписный режим:
он несовместим с пагинацией и не получает разделителей, которые могли бы попасть в документ.

### 5.7. Массовое чтение пакетов

Чтение 50–100 пакетов — штатный сценарий одного вызова CLI. Для него не нужны
50 отдельных команд, JSON, промежуточные Markdown-файлы или генератор скрипта.
Агент явно выбирает набор и объём сведений.

**Краткий обзор до 100 пакетов выбранного протокола:**

```bash
l2ref list --type packets --protocol protocol:152 --view brief --limit 100
```

Результат содержит адрес и название каждого пакета, аннотацию, выбранную редакцию,
краткие состояния и существенный технический контекст. Полные документы и объекты
источников не печатаются вместо краткой карточки.

**До 100 пакетов полностью, включая описание с Markdown, источники и вопросы:**

```bash
l2ref list --type packets --protocol protocol:152 --view full --limit 100
```

`packets` с `--protocol` означает карточки с явно выбранными применимыми редакциями.
В выводе различаются логический адрес пакета и адрес его технической редакции.
Без протокола полные технические тексты не выбираются произвольно: для чтения всех
редакций используется тип `packet-revisions` и их собственные адреса.

`--limit 100` означает не более 100 записей, а не обрезание каждого описания до
некоторой длины. Если найдено 52 пакета, возвращаются 52; если 180 — первые 100
с явным продолжением. Для всего отфильтрованного набора используется `--all`:

```bash
l2ref list --type packets --protocol protocol:152 --view full --all
```

**Уже известные адреса читаются вместе:**

```bash
l2ref read packet:key-packet packet:protocol-version packet:server-list \
  --protocol protocol:152 --view full
```

Таким же образом можно передать 50 или 100 адресов; показанные три — только короткий
пример формы команды. Исходный порядок сохраняется. Каждый результат начинается
с различимого заголовка с адресом, названием, редакцией и языком, затем идёт его
содержимое. Общая информация о запросе не повторяется внутри каждого объекта.

**Если документы длинные, агент читает их порциями, а не теряет часть вывода:**

```bash
l2ref list --type packets --protocol protocol:152 --view full --limit 10
# Следующая команда целиком подсказывается в конце результата:
l2ref list --type packets --protocol protocol:152 --view full --limit 10 --after <cursor>
```

Размер порции выбирается по задаче и объёму документов; CLI не обещает, что 100 полных
описаний всегда поместятся в контекст модели. Он не обрезает тела документов и
не объявляет частично показанную запись прочитанной целиком. Если ограничение накладывает
оболочка агента, агент использует меньшую порцию или выбор полей вместо повторного
неограниченного вывода.

**Необязательная фиксация набора для двухэтапного чтения:**

```bash
l2ref list --type packets --protocol protocol:152 --view brief --limit 50 \
  --save-selection ./packets.selection.json
l2ref read --selection ./packets.selection.json --protocol protocol:152 --view full
```

Это служебный файл адресов, не файл Markdown на каждый пакет. Он нужен только если
требуется сохранить именно показанный набор между вызовами. Выборка пакетов с
протокольным контекстом фиксирует также выбранные редакции: смена применимости не
должна незаметно подменять текст другой редакцией. При перечитывании CLI использует
зафиксированные адреса редакций и отдельно сообщает об изменившейся применимости.

## 6. Обзор структуры, связей и наполненности

| Команда                                             | Назначение                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| `status`                                            | Путь базы, состояние схемы, языки, краткие счётчики, актуальность экспорта |
| `types`                                             | Типы, пространства адресов и поддерживаемые операции                       |
| `stats [фильтры] --by <fields>`                     | Счётчики по типу, языку, статусу, региону или хосту источника              |
| `tree [key] [--depth <n>]`                          | Классификация и выпуски с копируемыми адресами                             |
| `relations <key> [--in\|--out] [--relation <name>]` | Входящие и исходящие связи с указанием их роли                             |

Счётчики источников различают количество вложенных объектов и количество уникальных
URL. Состояние исследования не вычисляется из количества ссылок.

`relations` отличает принадлежность, классификацию, техническую применимость и
упоминание в Markdown. Вычисленная связь помечается как вычисленная, а не выдаётся
за независимо редактируемое поле.

```bash
l2ref tree branch:main --depth 4
l2ref relations release:gracia-part-1
l2ref relations chronicle:gracia --in
l2ref stats --type protocols --by status
l2ref stats --has sources --by type,locale
```

## 7. Создание и изменение

### 7.1. `create`

```text
l2ref create <key> [поля типа] [--locale <code>]
                  [--title <text>] [--summary <text>]
                  [--description <text>] [--set-stdin <field>]
                  [--set-file <field=path>...]
                  [--set <field=value>...] [--add <field=value>...]
                  [--if-exists error|skip] [--dry-run]
```

- Тип и код выводятся из адреса; UUID назначается базой.
- Для редакции из адреса выводятся владелец и `rev`; для регионального контекста —
  его релиз и локальный код. Повторять эти сведения во входе не требуется.
- Ссылки на другие записи передаются логическими адресами, не UUID.
- Родительская группировка не включается в адрес самостоятельного релиза.
- По умолчанию существующая запись — ошибка, а не неявный `upsert`.
- `--if-exists skip` явно пропускает существующую запись и сообщает об этом;
  её поля не обновляются и не объявляются совпадающими с переданными значениями.
- Создание одного перевода не создаёт пустые копии остальных языков.
- Отсутствие источника допустимо при любом статусе.

```bash
l2ref create branch:main --title "Main"
l2ref create saga:the-chaotic-throne --branch branch:main --title "The Chaotic Throne"
l2ref create chronicle:the-kamael --branch branch:main --saga saga:the-chaotic-throne --title "The Kamael"
l2ref create release:the-kamael --chronicle chronicle:the-kamael --title "The Kamael"
l2ref create region:na --title "Северная Америка"
l2ref create release-context:the-kamael:na --region region:na
l2ref create protocol:152 --title "Игровой протокол 152"
```

Создание регионального контекста не назначает ему дату или протокол автоматически.

### 7.2. `update`

```text
l2ref update <key...> [--locale <code>] [изменяемые поля]
                     [--set <field=value>...] [--clear <field>...]
                     [--add <field=value>...] [--remove <field=value>...]
                     [--description <text>] [--set-stdin <field>]
                     [--set-file <field=path>...]
                     [--if-version <token>] [--dry-run]
l2ref update --selection <path> [те же изменения]
```

Основные предметные флаги:

| Поля / параметры                    | Смысл                                                    |
| ----------------------------------- | -------------------------------------------------------- |
| `--title`, `--summary`              | Изменить только текст выбранного языка                   |
| `--description`                     | Изменить основное описание выбранного языка              |
| `--set-stdin <field>`               | Передать многострочный текст одного поля через stdin     |
| `--set-file <field=path>`           | Записать конкретное текстовое поле из файла              |
| `--status`                          | Полнота предметного описания, не состояние перевода      |
| `--translation-status`              | Состояние конкретного перевода                           |
| `--order`                           | Редакционный порядок, не дата                            |
| `--released-on`                     | Дата регионального контекста с точностью года/месяца/дня |
| `--name`, `--server`, `--direction` | Собственные технические поля карточки пакета             |
| `--opcode`                          | Типизированный опкод выбранной редакции пакета           |

`--description` и `--set description=...` принимают настоящий многострочный текст,
а не только одну строку. `--set` применяется к остальным скалярным полям, известным схеме.
Он не является произвольным SQL или способом перезаписать внутренние поля базы.
Строковое значение `null` остаётся строкой; для очистки есть `--clear`.

`--set-file description=./draft.md` читает содержимое файла в указанное поле.
Механизм не привязан к Markdown и подходит для других текстовых полей, которые
разрешает схема. `--set-stdin description` явно выбирает stdin; низкоуровневая форма
`--set-file description=-` ему равнозначна. Для нескольких полей из файлов
параметр повторяется; не требуется вводить отдельный флаг файла для каждого нового поля.
Схема определяет допустимые поля, формат и ограничения содержимого.

В одном действии нельзя одновременно передать значение одного поля разными
способами, например `--description`, `--set-stdin description` и `--set-file description=...`. CLI сообщает
о конфликте до записи, а не выбирает значение по скрытому приоритету.

`--add` и `--remove` адресно изменяют списки скалярных значений, например `states`,
`servers` или `loginRevisions`. Схема проверяет тип каждого элемента. Добавление
существующего или удаление отсутствующего элемента — явно показанный no-op.
Этими параметрами нельзя обходить специальные операции переводов и источников
или правила предметных связей. При создании `--add` задаёт начальные элементы списка.

Значения перечислений: `--status missing|partial|documented`,
`--translation-status ready|missing|outdated`, `--server login|game`,
`--direction client-to-server|server-to-client`.
Дата `--released-on` принимает `YYYY`, `YYYY-MM`, `YYYY-MM-DD` с проверкой календаря.

Семантика очистки определяется типом и показана в схеме: nullable-поле становится
`null`, текст — пустым текстом, список — пустым списком. Обязательную предметную
связь очистить нельзя. Результат очистки явно показывается в diff.
Если необязательное поле не допускает пустое значение, например пояснение источника,
очистка удаляет это поле из объекта. Отсутствие поля не подменяется `null` или пустой строкой.

Критические гарантии:

- Непереданное поле не меняется.
- Изменение `title`, `summary` или `description` не затрагивает другие языки, источники и вопросы.
- Во внешнем интерфейсе обычного `update` нет замены всего массива переводов.
- Списки ссылок изменяются через `link`/`unlink`, источники и вопросы — через свои операции.
- Массовая замена структурированных данных допускается только отдельной явной
  операцией `replace` с полным diff и предусловием версии; это не скрытая семантика `update`.
- Изменение технической редакции показывает все протоколы, использующие её.
  Фильтр чтения одного протокола не делает переиспользуемую редакцию локальной для него.

```bash
l2ref update release:gracia-part-1 --locale ru --title "Gracia Part 1"
l2ref update release-context:gracia-part-1:na --released-on 2000-01 --dry-run
l2ref update chronicle:the-kamael --clear saga --dry-run
l2ref update packet:key-packet:rev-1 --opcode u8:0x00 --dry-run
l2ref update protocol:152 --add loginRevisions=30810 --dry-run
l2ref update packet:key-packet:rev-1 --add states=authenticated --dry-run
```

Формат опкода: компоненты `тип:значение`, разделённые `/`, например
`u8:0xFE/u16le:0x0012`. Десятичные и шестнадцатеричные значения допустимы;
CLI проверяет разрядность, сохраняет известный ноль и отличает его от неизвестного опкода.

### 7.3. Многострочный текст без создания файлов

Это обычный основной сценарий, а не обход CLI и не повод требовать JSON.
Одна команда может содержать много строк; «один вызов CLI» не означает «одна строка текста».

| Способ                                        | Когда использовать                                                                    |
| --------------------------------------------- | ------------------------------------------------------------------------------------- |
| `--description=<text>` / `--set <field=text>` | Обычный прямой ввод одного или нескольких текстовых полей                             |
| `--set-stdin <field>`                         | Длинный текст, heredoc или конвейер без промежуточного файла                          |
| `--set-file <field=path>`                     | Уже существующий черновик, повторное использование файла или отдельное редактирование |

Для нескольких полей `--set` повторяется. Если в будущем схема конкретного типа
предусмотрит два поля с Markdown, например `description` и `notes`, они передаются
в одном вызове без двух файлов. Следующий пример предполагает именно такую схему
и сам по себе не добавляет `notes` в предметную модель:

```bash
l2ref update release:the-kamael --locale ru \
  --set 'description=# Основное описание

Первый многострочный текст.' \
  --set 'notes=## Примечания

Второй независимый многострочный текст.'
```

Для длинного текста и содержимого с кавычками предпочтителен блок многострочного
ввода оболочки (`heredoc`) с разделителем в кавычках:

```bash
l2ref update release:the-kamael --locale ru --set-stdin description --dry-run <<'L2REF_TEXT'
# Описание релиза

Первый абзац.

- Первый пункт
- Второй пункт

Маркеры {{link chronicle:the-kamael}}, символы $ и `код` остаются текстом.
L2REF_TEXT
```

В поле поступают реальные переносы строк, не строка с литералами `\n`.
Кавычки в `<<'L2REF_TEXT'` запрещают подстановки переменных и выполнение команд
оболочкой внутри блока. Они не убирают переносы и не становятся частью описания.
Разделитель выбирается так, чтобы он не встречался отдельной строкой в содержимом.

Гарантии и ограничения:

- Текст — данные. CLI не выполняет его как код и не интерпретирует Markdown как команды оболочки.
- CLI не обрезает пробелы, отступы, пустые строки и завершающий перевод строки.
  Литералы `\n` не превращаются в переносы автоматически.
- `--set` разделяет имя поля и значение только по первому `=`; остальные `=` принадлежат тексту.
- Одноимённые поля из аргумента, stdin, файла и структурированного ввода конфликтуют,
  а не перезаписываются скрыто.
- У процесса один stdin. `--set-stdin` заполняет только одно поле; его нельзя одновременно
  использовать для второго поля, `--keys-file -` или `--input -`.
- Остальные поля того же действия можно передать обычными аргументами. Для нескольких
  очень больших полей доступны отдельные команды либо структурированный пакет через stdin,
  если нужна общая транзакция; промежуточный файл при этом не обязателен.
- Большие аргументы ограничены операционной системой; для таких документов CLI рекомендует
  stdin, а не создание обязательного файла. Собственные ограничения размера ввода явно
  описаны в справке и диагностике, не приводят к молчаливому усечению.
- Канал передачи не меняет валидацию, язык, diff, атомарность или защиту версии.
  Изменяется только указанное поле, а не весь перевод.
- Если используется передача аргументом, экранирование выполняется правилами оболочки;
  для текста из внешних источников рекомендуются quoted heredoc или передача аргументов
  без интерпретации оболочкой. Промежуточная подстановка `$(...)` не рекомендуется:
  она может удалить завершающие переводы строк.

## 8. Связывание, переводы и вложенные сведения

### 8.1. `link` и `unlink`

```text
l2ref link <from> <relation> <to...> [--replace] [--unscoped]
           [--before <key> | --after <key>] [--dry-run]
l2ref unlink <from> <relation> <to...> [--dry-run]
l2ref unlink <from> <relation> --all [--dry-run]
```

- Имена связей предметные: `branch`, `saga`, `chronicle`, `region`, `countries`, `protocols`.
  Схема конкретного типа перечисляет допустимые исходящие связи и их кратность.
- Добавление элемента в M:N не заменяет весь список. Повтор уже существующей связи —
  явно показанный no-op.
- Для упорядоченной множественной связи допустимы `--before <existing-key>` или
  `--after <existing-key>`. Явно заданная позиция может переместить существующую связь;
  это отдельное изменение порядка в diff, не молчаливая переупорядоченность списка.
- Для одиночной связи замена существующей цели требует `--replace`.
- Ссылки на владельца, входящие в состав адреса редакции или регионального контекста,
  неизменяемы. Через `link` нельзя опосредованно переименовать такую запись.
- `unlink` убирает только связь, не удаляет целевую запись.
- Обязательную одиночную связь нельзя разорвать, оставив невалидную запись.
- Обратные и вычисленные связи не записываются как отдельные копии факта.
- Для смены хроники релиза меняется только классификация; адрес и UUID сохраняются.
- Привязка протокола к знанию требует адрес технической редакции. CLI не выбирает её
  для записи по принципу «последняя» или «пока единственная».
- Если у карточки уже выбрана другая редакция для этого протокола, обычный `link`
  сообщает конфликт. Явный `--replace` атомарно переносит применимость с полным diff.
- Прямой протокол релиза без регионального контекста требует явного `--unscoped`.
  CLI не размножает его по регионам и не принимает за региональную применимость.

```bash
l2ref link release:gracia-part-1 chronicle chronicle:gracia --replace --dry-run
l2ref link release-context:gracia-part-1:na protocols protocol:152
l2ref link packet:key-packet:rev-1 protocols protocol:152
l2ref unlink release-context:gracia-part-1:na protocols protocol:152
```

### 8.2. Переводы

```text
l2ref translation list <key>
l2ref translation set <key> [--locale <code>] [--title ...] [--summary ...]
                          [--description ...] [--set-stdin <field>]
                          [--set-file <field=path>...]
                          [--translation-status ...] [--dry-run]
l2ref translation delete <key> [--locale <code>] [--dry-run]
```

`translation set` создаёт отсутствующий перевод или изменяет только переданные поля
существующего. Он не копирует текст из другого языка и не удаляет соседние переводы.
Флаги текста в `create`/`update` используют тот же контракт, а не отдельные правила слияния.
Если язык не передан, используется основной язык базы; фактический язык всегда
указан в предпросмотре и результате.

Удаление перевода — отдельная операция, а не передача массива с одним оставшимся языком.
Diff показывает удаляемый Markdown, источники и вопросы этого перевода.

### 8.3. Технические редакции

```text
l2ref revision list <card-key>
l2ref revision add <card-key> [--rev <n>] [--from <revision-key>]
                           [поля редакции] [--dry-run]
```

Если `--rev` не задан, следующий номер назначается атомарно внутри карточки и
показывается в результате. Это технический номер справочника, не номер релиза игры.

Копирование `--from` переносит явно описанное содержимое, но не назначает
применимость к протоколам автоматически. UUID вложенных источников нового владельца
назначаются заново. Изменение существующей редакции выполняется обычным `update`
по её полному адресу; удаление — `delete` по этому же адресу.

### 8.4. Источники

```text
l2ref source list <key> [--locale ... | --all-locales]
l2ref source add <key> [--locale <code>] --url <url> --title <text> [--summary <text>]
l2ref source update <key> [--locale <code>] (--id <id> | --match-url <url>) [изменяемые поля]
l2ref source remove <key> [--locale <code> | --all-locales]
                    (--id <id> | --match-url <url> | --match-host <host>) [--all-matches]
l2ref source remove --selection <path> [те же параметры языка и совпадения]
l2ref source clear <key...> (--locale <code> | --all-locales) [--dry-run]
l2ref source clear --selection <path> (--locale <code> | --all-locales) [--dry-run]
```

- Источник принадлежит конкретному переводу. Владелец и язык всегда видны в выводе.
- Поля изменения источника: `--url`, `--title`, `--summary`; очистка необязательного
  пояснения выполняется через `--clear summary`. Идентификатор источника не меняется.
- UUID назначается автоматически. Обычное добавление не требует предварительного чтения владельца.
- Изменить источник можно по точному текущему URL, не узнавая UUID заранее.
  `--match-url` выбирает существующий источник, а `--url` задаёт новое значение.
- Если выбор по URL неоднозначен, CLI показывает совпадения и требует точный ID;
  для удаления допустим отдельный явный `--all-matches`. Первое совпадение не выбирается автоматически.
- Удаление по хосту поддерживает точечную очистку без удаления остальных источников
  владельца. Охват нескольких совпадений явно задаётся `--all-matches`.
- Очистка одного языка не очищает остальные языки.
- Одиночные действия используют общий язык по умолчанию. Для `clear` область задаётся
  явно: `--locale` либо `--all-locales`, чтобы слово «очистить» не скрывало охват удаления.
- Наличие источников не является обязательным ни для одного статуса или региона.
- CLI не добавляет URL текущего проекта или другую ссылку как «доказательство» автоматически.
- Проверка формы URL не означает сетевую проверку его доступности или достоверности сведений.

### 8.5. Открытые вопросы

```text
l2ref question list <key> [--locale ... | --all-locales]
l2ref question add <key> [--locale <code>] --text <text>
l2ref question remove <key> [--locale <code>] --text <exact-text>
l2ref question clear <key> (--locale <code> | --all-locales) [--dry-run]
```

Неизменённый повтор вопроса может завершаться явным no-op. Числовой номер строки
вывода не используется как устойчивый идентификатор для последующего удаления.

## 9. Удаление, замена и стабильность адресов

```text
l2ref delete <key...> [--cascade-owned] [--allow-broken-links]
                     [--if-version <token>] [--dry-run]
l2ref delete --selection <path> [те же параметры]
l2ref replace <key> --input <path|-> --if-version <token> [--dry-run]
```

- Обычный `delete` не удаляет связанные самостоятельные записи, чтобы устранить FK-конфликт.
- Собственные тексты и вложенные объекты удаляются вместе с записью.
- Удаление отдельных принадлежащих записей, например технических редакций карточки,
  требует `--cascade-owned`; перечень и объём удаления показываются заранее в diff.
- Хроника не владеет жизненным циклом своих релизов. Удаление группы не означает
  удаление релизов, протоколов или региональных выходов.
- При препятствующих связях ошибка показывает ссылающиеся адреса и предлагает
  перенести связь или явно удалить нужные записи одним батчем.
- Упоминания в Markdown проверяются отдельно от SQL-связей. Новые неразрешённые
  ссылки, создаваемые удалением, показываются; их сохранение требует явного `--allow-broken-links`.
- `replace` — сознательная полная замена, в том числе списков и переводов.
  Это не предпочтительный путь изменения одного поля.
- Его вход соответствует редактируемой записи представления `edit`; автоматически
  назначенные поля не требуется восстанавливать вручную. Переданные идентификаторы
  проверяются как неизменяемые. Оболочка метаданных чтения не является полем записи.
- Нет универсального `--force`, отключающего валидатор или внешние ключи.

Переименование устойчивого кода не включается в обычный `update` или `replace`.
Отдельная операция переименования требует собственного решения о Markdown-ссылках,
внешних файлах и совместимости адресов. Нельзя обещать полное автоматическое
исправление ссылок за пределами базы; алиасы также не вводятся скрыто этим CLI-проектом.

## 10. Предпросмотр, версии и массовые операции

### 10.1. Один и тот же план для проверки и записи

Любая предметная запись поддерживает `--dry-run`, включая связи, переводы,
источники, вопросы, удаления и пакет изменений.

Предпросмотр показывает:

- адреса и названия затронутых записей;
- конкретный язык и поле;
- прежнее и новое значение;
- добавленные и удалённые связи, источники, вопросы;
- удаляемые переводы и принадлежащие записи;
- протоколы, затрагиваемые изменением переиспользуемой редакции;
- предупреждения о Markdown-ссылках;
- число записей без изменений;
- исходную версию снимка, которую можно передать в `--if-version`.

```text
Будет изменён релиз release:gracia-part-1 — Gracia Part 1

  translation.ru.title:
    было: «Gracia I»
    станет: «Gracia Part 1»

  translation.en: без изменений
  sources: без изменений
  protocols: без изменений

Запись не выполнена. Изменится 1 запись.
```

Для добавляемого источника показывается URL, а не только имя поля `translations`.
Для очистки показываются область языка и количество удаляемых источников.
`--dry-run` по умолчанию показывает `--diff full`. Обычная запись использует
`--diff summary`: конкретные изменённые поля и существенные значения, область языка,
адреса связей, URL добавляемых источников, число изменённых строк Markdown — без
повторной распечатки полного документа. `--diff full` запрашивается и при реальной записи.
При сокращённом diff вывод сообщает, какие подробности не показаны и как получить
полный вариант. В полном diff значения не обрезаются молча.

UUID будущих объектов не нужны для осмысленного предпросмотра. Расчётная будущая
ревизия не выдаётся за текущую или уже сохранённую версию базы.
Предпросмотр и запись используют одинаковые правила расчёта. `--if-version`
защищает состояние базы, но не фиксирует содержимое внешнего Markdown-файла:
для воспроизводимого применения входные файлы между вызовами не должны меняться.

### 10.2. Защита от устаревшего чтения

```bash
l2ref read release:gracia-part-1 --view edit --with-version
l2ref update release:gracia-part-1 --title "Gracia Part 1" --if-version <token>
```

Токен непрозрачен и не является идентификатором релиза. В выводе для копирования он
полный, не укороченный хеш. Обычный вывод не повторяет версии на каждом уровне дерева.

При конфликте CLI не перечитывает базу и не повторяет запись автоматически. Он
объясняет, что нужно обновить исходное чтение или выборку. Атомарность, проверка
конечного состояния и отсутствие частичной записи обязательны и без явного токена.

### 10.3. Сохранённая выборка

Изменение по критерию не должно незаметно захватывать записи, появившиеся после
просмотра. Для массовых действий предпочтительна сохранённая выборка:

```bash
l2ref list --has sources --source-host example.invalid --all-locales --all --save-selection ./sources.selection.json
l2ref source remove --selection ./sources.selection.json --match-host example.invalid --all-matches --all-locales --dry-run
l2ref source remove --selection ./sources.selection.json --match-host example.invalid --all-matches --all-locales
```

Файл выборки — системный артефакт: версия формата, точные адреса, исходный запрос и
версия снимка. Он не содержит исполняемых выражений и не является SQL-запросом.
Повторная запись по устаревшей выборке завершается конфликтом, а не затрагивает иной набор.
Чтение по выборке использует зафиксированные адреса и явно сообщает версию текущего
чтения; при её отличии от исходной показывает предупреждение. Это позволяет перечитать
те же записи после изменения. Файл выборки не переключает базу неявно.

Выборка фиксирует владельцев, а не превращает поисковый критерий в скрытый фильтр
записи. Поэтому условие удаления источников передаётся явно через `--match-host`
или `--match-url`. `source remove` сохраняет остальные источники; `source clear`
намеренно удаляет все источники выбранных владельцев в указанной языковой области.

Массовая запись принимает перечисленные адреса или сохранённую выборку, но не
повторяет поисковый запрос для определения нового набора в момент записи.
Нельзя трактовать страницу списка как весь набор. `unlink --all` означает все связи
указанного вида только у одного владельца, а `--all-locales` — языки, не все записи базы.
Ноль совпадений — явно показанный no-op, не повод расширить критерий поиска.

## 11. Батчинг

Батч предназначен для агента и системных сценариев. От него не требуется тот же
пошаговый человекоориентированный вывод, что от одиночных команд, но предметные
операции и гарантии безопасности должны совпадать.

```text
l2ref batch --input <path|-> [--dry-run] [--if-version <token>]
```

Требования:

- Один пакет — одна транзакция, без частичного успеха.
- Операции имеют тот же смысл, что `create`, `update`, `translation set`, `link`,
  `unlink`, `source add/remove/clear`, `question add/remove/clear` и `delete`.
- Адрес передаётся один раз. Нет оболочек `entry.value.key`, повторного `code`,
  обязательного UUID, SQL-имён таблиц и ручного `kind: implementation`.
- Перевод редактируется по владельцу и языку, без передачи всех остальных переводов.
- Можно ссылаться на адреса записей, создаваемых в том же пакете.
- Проверка предметных ссылок выполняется по конечному состоянию пакета.
- Зависимые операции имеют явно определённый порядок: создание, затем изменение
  того же адреса допустимы; изменение после его удаления — ошибка.
- Разные текстовые и предметные поля одного адреса можно менять несколькими операциями.
  Они применяются в порядке пакета; последняя явная запись одного скалярного поля побеждает.
- Файлы текстовых полей читаются и вход проверяется до начала SQL-записи.
- `values` содержит непосредственные значения, `files` — пути файлов по именам полей.
  Одно поле нельзя одновременно задать в `values` и `files` одной операции.
- Пути в файле пакета отсчитываются от каталога этого файла; для stdin — от cwd.
- Ошибка содержит индекс операции, адрес, язык, поле, проблемное значение и причину.
- Итог содержит счётчики и при необходимости общий diff; JSON доступен явно.

Пример системного ввода, не обязательного для обычной работы:

```json
{
  "formatVersion": 1,
  "operations": [
    {
      "op": "create",
      "key": "release:gracia-part-1",
      "locale": "ru",
      "values": {
        "chronicle": "chronicle:gracia",
        "title": "Gracia Part 1",
        "summary": "Краткое описание релиза"
      },
      "files": {
        "description": "./gracia-part-1.ru.md"
      }
    },
    {
      "op": "translation.set",
      "key": "release:gracia-part-1",
      "locale": "en",
      "values": {
        "title": "Gracia Part 1",
        "summary": "Release summary"
      }
    },
    {
      "op": "link",
      "key": "packet:key-packet:rev-1",
      "relation": "protocols",
      "targets": ["protocol:152"]
    }
  ]
}
```

## 12. Справка, схемы и ошибки

### 12.1. Справка доступна до наполнения базы

```bash
l2ref help
l2ref help create
l2ref help create --type releases
l2ref help workflow catalog
l2ref help workflow translate
l2ref help workflow research
l2ref help relations
```

Справка каждой команды содержит назначение, обязательные параметры, умолчания,
семантику отсутствующих значений, последствия записи и минимальный рабочий пример.
Примеры используют реальные имена параметров целевого интерфейса, а не внутренние DTO.

### 12.2. Схема описывает ввод операции

```bash
l2ref schema create --type releases
l2ref schema update release:gracia-part-1
l2ref schema translation.set release:gracia-part-1
l2ref schema link packet:key-packet:rev-1 protocols
l2ref schema batch
```

Идентификатор операции `translation.set` соответствует обычной команде
`translation set` и той же операции внутри батча. Это не отдельная семантика перевода.

По умолчанию это краткая текстовая инструкция:

```text
Создание релиза

Адрес: release:<code>

Обязательно:
  chronicle  Адрес хроники-группы; флаг --chronicle.

Необязательно:
  title      Заголовок выбранного языка; флаг --title.
  summary    Краткое описание; флаг --summary.
  description  Основное описание; формат Markdown.
               Прямой многострочный текст: --description.
               Из stdin: --set-stdin description.
               Из существующего файла: --set-file description=<path>.

UUID и код отдельно передавать не нужно.
```

- Технические имена `title`, `summary`, `description`, `chronicle` не переводятся.
  Русские подписи дополняют их, а не заменяют ключи.
- UUID и другие автоматически назначаемые поля не объявляются обязательным вводом.
- Схемы `create`, `update`, `replace`, переводов и батча разные там, где различается контракт.
- В текстовом режиме нет рекурсивной распечатки всех деталей Zod/JSON Schema.
- `schema ... --format json` возвращает полноценную машиночитаемую схему именно этой операции.
- По адресу схема может определяться без существующей записи; проверка актуального
  состояния записи — отдельное действие, не условие получения справки.

### 12.3. Ошибка объясняет следующий шаг

```text
Не удалось изменить release:gracia-part-1.

Поле chronicle ссылается на отсутствующую запись chronicle:gracia.
Никакие изменения не сохранены.

Проверить группу:
  l2ref read chronicle:gracia --view brief

Посмотреть допустимый ввод:
  l2ref schema update release:gracia-part-1
```

Обязательные составляющие диагностики:

- действие и адрес;
- конкретное поле и язык, если применимо;
- проблемное значение или адрес цели;
- понятная причина и допустимое исправление;
- для файла — путь и доступное место ошибки, для батча — индекс операции;
- явное сообщение о том, была ли запись выполнена.

Стек вызовов не выводится вместо диагностики. Системный код ошибки остаётся стабильным
и доступен в JSON. При нескольких ошибках CLI собирает доступные независимые ошибки;
если проверка остановлена по лимиту, это явно сказано, а остальные записи не объявлены проверенными.

## 13. Требования к текстовому выводу

### 13.1. Список — это список, а не дерево сериализованного объекта

```text
===== PAGE q31c4 BEGIN | list | записи 1–2 из 4 | brief | ru =====
Область: релизы хроники chronicle:gracia

----- RECORD q31c4 1/4 BEGIN | Релиз | release:gracia-part-1 -----
Название: Gracia Part 1
  Кратко: ...
  Язык: ru · Полнота описания: частично · Перевод: готов
----- RECORD q31c4 1/4 END | Релиз | release:gracia-part-1 -----

----- RECORD q31c4 2/4 BEGIN | Релиз | release:gracia-part-2 -----
Название: Gracia Part 2
  Кратко: ...
  Язык: ru · Полнота описания: не описано · Перевод: готов
----- RECORD q31c4 2/4 END | Релиз | release:gracia-part-2 -----

===== PAGE q31c4 END =====
Показано 2 записи из 4. Осталось 2.
Продолжить: l2ref list --type releases --chronicle chronicle:gracia --view brief --locale ru --limit 2 --after <cursor>
```

- Адрес доступен для копирования и не обрезается по ширине терминала.
- Нет восьми повторяющихся служебных строк для каждой короткой записи.
- Длинные значения переносятся без потери содержимого.
- Отсутствующая аннотация отмечается как «краткое описание не заполнено», а не выдумывается.
- `0 записей`, пустой список, неизвестное значение и отсутствующий перевод различаются словами.
- Цвет и символы оформления не являются единственным носителем смысла.

### 13.2. Полная запись — документ с контекстом

Порядок блоков: тип, название и адрес; язык и выбор редакции; существенные предметные
поля; краткое описание; основное описание и другие текстовые поля; связи; источники; вопросы.

Markdown отделён от служебных блоков, но не получает искусственных отступов,
меняющих смысл списков и блоков кода. Несколько полей с Markdown не смешиваются в один
документ. Для буквального чтения конкретного поля есть `--content description`.
Состояния называются по смыслу: «полнота описания», «состояние перевода», «применимость»,
а не несколькими неразличимыми полями «состояние».

### 13.3. Обычная запись — понятное подтверждение действия

```text
Изменён release:gracia-part-1 — Gracia Part 1

  Русский заголовок: «Gracia I» → «Gracia Part 1».
  Другие языки, Markdown, источники и связи не изменены.

Сохранено: 1 запись.
```

Сообщение соответствует фактическому действию: «создано», «изменено», «связь добавлена»,
«удалено», «пропущено», «без изменений» или «только проверено».
Для удаления видны адрес и название; для источника — URL и язык; для связи — оба адреса и её роль.
Хеши, вложенные UUID и внутренние SQL-имена не вытесняют предметный результат.

### 13.4. Границы страниц, записей и текстовых полей

При списочном, поисковом и множественном чтении границы должны быть понятны без
интерпретации самого Markdown. Заголовок документа, горизонтальная черта или текст
«следующая запись» внутри поля не являются управляющей разметкой CLI.

Контракт текстового оформления:

1. У страницы есть маркеры начала и конца.
2. У каждой записи — собственные маркеры начала и конца с одинаковыми сквозным
   номером, типом и полным логическим адресом. Если выбирается редакция знания,
   отдельно показан её точный адрес.
3. Каждое поле с Markdown или другим многострочным текстом имеет собственные границы,
   имя поля и область языка. Два поля с Markdown или два перевода не склеиваются.
4. Содержимое поля между границами остаётся буквальным: CLI не добавляет к каждой
   строке отступ, префикс номера записи или экранирование Markdown.
5. Короткая метка вывода в примере `q7f2a` связывает служебные границы одной страницы.
   Она не является адресом записи, версией базы или курсором для `--after`.
6. Маркеры подбираются так, чтобы не совпадать с показанным содержимым. При коллизии
   меняется или удлиняется служебная метка, а не редактируется авторский текст.
7. Недоступная запись тоже имеет завершённый блок с причиной. Её состояние не
   переносится на следующую сущность и не обозначается пустым блоком без пояснения.
8. Разделители существуют и без цвета, и вне TTY. Их смысл не зависит от ширины терминала.

Иллюстрация полного смешанного чтения двух записей на странице:

```text
===== PAGE q7f2a BEGIN | read | записи 1–2 из 5 | full | ru =====

----- RECORD q7f2a 1/5 BEGIN | Хроника | chronicle:gracia -----
Название: Gracia
Язык: ru

<<< FIELD q7f2a 1 description ru BEGIN | Markdown >>>
# Описание группы

Текст описания хроники.
<<< FIELD q7f2a 1 description ru END >>>

----- RECORD q7f2a 1/5 END | Хроника | chronicle:gracia -----

----- RECORD q7f2a 2/5 BEGIN | Протокол | protocol:152 -----
Название: Игровой протокол 152
Язык: ru

<<< FIELD q7f2a 2 description ru BEGIN | Markdown >>>
# Описание протокола

Текст описания протокола.
<<< FIELD q7f2a 2 description ru END >>>

----- RECORD q7f2a 2/5 END | Протокол | protocol:152 -----

===== PAGE q7f2a END =====
Показано 2 записи из 5. Осталось 3.
Продолжить: l2ref read chronicle:gracia protocol:152 protocol:273 release:gracia-part-1 region:na --view full --locale ru --limit 2 --after <cursor>
```

В `brief` поля короткие, но границы записей и страницы остаются явными; отсутствие
полного текста — свойство представления, а не незаметное усечение документа.
В `--content` вся эта служебная разметка отсутствует.

Если оболочка агента сообщает об усечении или пропуске части вывода, страница не
считается полностью полученной даже при видимом конечном маркере: оболочка могла
оставить начало и конец, пропустив середину. Отсутствие конечного маркера также
сигнализирует незавершённую выдачу. Агент уменьшает порцию или получает пропущенное
содержимое; он не переходит по следующему курсору, считая весь блок уже прочитанным.

## 14. Системный JSON и потоки

- `--format json` не меняет состав выбранных данных, правила выбора или смысл операции.
  Различается кодирование и отсутствие человекоориентированного оформления.
- При успешном запросе stdout содержит один JSON-документ без префиксов, ANSI,
  прогресса и справочных сообщений. При ошибке исполнения stdout пуст, а stderr
  содержит один JSON-документ ошибки.
- У ответа стабильная оболочка: `ok`, `data`, `meta`; у ошибки — `ok: false`, `error`.
- Метаданные чтения содержат область, представление, язык, пагинацию и версию снимка.
- Для страницы отдельно доступны `meta.page.start`, `end`, `returned`, `total`,
  `remaining`, `hasMore`, `nextCursor`. Наличие следующей страницы не смешивается
  с недоступностью отдельных записей. Текстовые маркеры в JSON не вставляются:
  границы задаются структурой объектов, их типами, адресами и метаданными.
- Результат записи различает выполненный no-op, сохранённое изменение и `dry-run`.
- Системные имена полей, коды ошибок и типы значений не локализуются.
- Текстовые данные и результаты идут в stdout; ошибки и диагностический прогресс — в stderr.
- В режиме `--content` stdout принадлежит содержимому поля целиком; сведения о ходе чтения туда не добавляются.
- Прогресс длительных действий не использует альтернативный экран и не засоряет не-TTY вывод.
- Закрытие читающей стороны конвейера не печатает стек `EPIPE`.
- Справка также имеет системное представление структуры команд, а не только JSON-строку с текстом help.

Предлагаемые коды завершения: `0` — успех, в том числе no-op и пустой поиск;
`1` — неожиданный сбой; `2` — неверные аргументы или данные; `3` — запрошенная запись
не найдена; `4` — конфликт версии или существования; `5` — временная недоступность базы.
Для множественного `read` отсутствующие адреса перечисляются в результате, общий код
`3` сигнализирует неполное чтение; найденные записи не теряются. `--allow-missing`
разрешает явно ожидаемые пропуски и возвращает `0`, не меняя их представление.
Неполное множественное чтение — обработанный запрос, не ошибка исполнения:
JSON-результат остаётся в stdout с `ok: true` и `meta.itemsComplete: false`; состояния
каждого элемента показывают пропуски. Запрос одной отсутствующей записи либо
невозможность выбрать требуемую редакцию для `--content` завершается
обычной диагностикой в stderr без подстановки поясняющего текста в документ.
`itemsComplete` описывает доступность запрошенных данных на показанной странице,
а не достижение конца выборки и не полноту исторического исследования. Для конца
выборки используется `hasMore: false`, для состояния знания — его предметный `status`.

## 15. Языки, проверка и обмен

```text
l2ref locale list
l2ref locale add <code> [--dry-run]
l2ref locale set-default <code> [--dry-run]
l2ref locale delete <code> [--dry-run]
l2ref validate [key...] [--selection <path>] [--links] [--strict-links]
l2ref export [--output <directory>] [--dry-run]
l2ref import --input <directory> --replace [--if-version <token>] [--dry-run]
l2ref init [--locales ru,en] [--default-locale ru]
```

- Для добавления языка не требуется писать SQL или подменять полный снимок базы.
- Удаление используемого или основного языка ограничено зависимостями и не удаляет переводы скрыто.
- `validate` без адресов проверяет всю базу; с адресами — записи и необходимые для их
  проверки зависимости, а не объявляет проверенной всю базу.
- Проверка Markdown выбирает поля по объявленному в схеме формату, а не по имени
  `description` или другому фиксированному списку. Аннотации источников не считаются
  Markdown и не разбираются как директивы без отдельного решения предметной модели.
- Неизвестность исследования сама по себе не ошибка. Проверка существования ссылки
  не доказывает историческую достоверность или совместимость протоколов.
- Экспорт — явное обновление генерируемого снимка для Git. CLI не делает commit, push
  или импорт после обычного предметного изменения.
- Импорт — полная замена, а не способ обновить один текст. Он требует явного `--replace`,
  поддерживает предпросмотр и проверяет вход до изменения рабочей базы.
- Неуспешный импорт не оставляет частично заменённую структуру или данные.
- `init` не заменяет существующую базу.

## 16. Производительность и проверка готовности

### 16.1. Требования к реализации

- Список, счётчики и краткий поиск не читают все Markdown-тексты и переводы базы,
  если они не нужны выбранному запросу.
- Фильтрация и пагинация выполняются до материализации полных записей.
- Один составной запрос читает согласованный снимок. Страничный обход не маскирует
  смену версии базы; сохранённая выборка фиксирует состав массовой операции.
- Все изменения остаются в проверяемом предметном API. Универсальный SQL-write
  не является заменой недостающих удобных команд.
- CLI должен быть удобен без запуска Python/Node для обычного чтения, наполнения,
  правки переводов, изменения связей и очистки выбранных источников.
- Скрипты и JSON остаются допустимыми инструментами сложной автоматизации;
  удобство CLI не обеспечивается запретом других инструментов.

### 16.2. Приёмочные сценарии

Каждый сценарий проверяется **в основном текстовом режиме**, затем — на эквивалентность
системного JSON. Батч дополнительно проверяется как самостоятельный системный интерфейс.

1. По help и schema создать ветку, сагу, хронику и одноимённый единственный релиз
   без чтения исходников, UUID, `base` и JSON-конвертера.
2. Выбрать заголовки и аннотации ста записей одним вызовом; явно получить тот же
   набор полностью с Markdown и всеми языками.
3. Найти строку только в Markdown каталога и URL только в источнике — без обязательного протокола.
4. Прочитать смешанный набор `chronicle:…`, `release:…`, `region:…`, `packet:…`
   и нескольких `protocol:…` без угадывания командной группы или лишнего контекста.
   Не использовать позиционные адреса протоколов как неявные селекторы редакций пакетов.
5. Сохранить Markdown в файл и прочитать его обратно без изменения пробелов и ограждений кода.
6. Изменить только русский заголовок или документ, сохранив английский перевод,
   источники, вопросы и применимость.
7. Создать и удалить отдельный перевод без замены всего массива языков.
8. Добавить и убрать одну связь, сохранив остальные; перенести релиз в другую хронику
   без изменения адреса и региональных выходов.
9. Увидеть конкретные URL и языки в предпросмотре очистки источников; выполнить
   очистку по фиксированной выборке без прямого SQL.
10. Получить понятную ошибку с полем и отсутствующим адресом и исправить её по подсказке.
11. Убедиться, что все результаты страницы не выдаются за весь набор, а `--all`
    действительно возвращает всё без скрытого лимита.
12. Получить конфликт при устаревшей версии и не увидеть автоматического повтора записи.
13. Выполнить пакет со связанными новыми записями, адресными правками переводов и
    Markdown-файлами; ошибка одной операции не сохраняет предыдущие операции.
14. Прочитать текстовый список без распечатки внутреннего объекта на десятки строк
    для каждой записи; увидеть понятный предметный результат одиночного изменения.
15. Не потерять различия между `null`, пустым текстом, пустым списком, известным нулём
    и отсутствующим переводом ни в одном формате.
16. Записать многострочное описание напрямую аргументом и через stdin без временного
    файла; сравнить реальные переносы, отступы, кавычки, `$`, обратные кавычки и
    завершающий перевод строки с исходным содержимым.
17. Для тестового типа с двумя текстовыми полями записать оба многострочных значения
    одним вызовом через повторяемый `--set`, не создавая по файлу на каждое поле.
18. Прочитать 50–100 пакетов кратко и полностью одним вызовом, без скрытого лимита
    в 50 адресов. При чтении порциями сохранить порядок, протокол и выбранные редакции;
    не обрезать тела документов и не терять остаток выборки.
19. Прочитать смешанный набор порциями и проверить сквозные номера, границы страниц,
    записей и текстовых полей. Markdown с заголовками и похожими на разделители строками
    не должен подменять служебные границы.
20. При отсутствии записи, изменении базы между страницами или усечении вывода
    оболочкой не перепутать эти состояния с полным успешным чтением всего набора.

Готовность определяется этими сценариями, а не только наличием команд или успешным
разбором JSON. Имена флагов, представления, схемы ввода, диагностика и примеры должны
образовывать один согласованный интерфейс.
