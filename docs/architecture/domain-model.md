# Предметная модель

Действующая модель базы: схема **19**. Физическое представление описано в
[матрице таблиц](table-matrix.md), операции — в [контракте базы](database-contract.md).

## Каталог и протокол

| Понятие        | Смысл и связи                                                          |
| -------------- | ---------------------------------------------------------------------- |
| Ветка          | Линия развития игры. Расширяемый справочник, например Main или Classic |
| Хроника        | Именованное обновление, принадлежащее одной ветке                      |
| Выпуск хроники | Самостоятельная часть или выпуск хроники со своим `code`               |
| Протокол       | Различимый технический контекст, по которому выбираются знания         |

```text
Ветка → Хроника → Выпуск ↔ Протокол
```

Выпуск и протокол связаны многие-ко-многим. В протоколе нет дублирующих ссылок на
ветку или хронику. Допустимы хроника без выпусков, выпуск без протоколов и протокол
без установленной принадлежности к выпуску.

Выпуск без отдельного именованного этапа может иметь `code: base`. Это обозначение
не устанавливает хронологию или приоритет. Порядок отображения также не является
датой выхода игры.

Протокол имеет реальный игровой `number` и наш `variant`:

| number | variant | Публичный ключ       |
| ------ | ------- | -------------------- |
| 152    | 0       | `protocol:152`       |
| 152    | 1       | `protocol:152-rev-1` |
| 152    | 2       | `protocol:152-rev-2` |

`variant` различает записи с одинаковым номером. Он не объявляет официальную
ревизию, порядок обновлений или совместимость. Первоначальный профиль сохраняет
обозначение без суффикса при появлении дубликатов.

Игровой номер обязателен. Пока он не установлен, исследование можно сохранять
в описании выпуска; неизвестность не заменяется выдуманным номером.
Login-номера, регион, ветка и сборка клиента имеют самостоятельный смысл.
Регионы и Login-номера хранятся как справочные признаки протокола. Отдельных
сущностей клиентской сборки, оператора и региональной даты выпуска пока нет.

## Карточка знания и техническая редакция

Три вида знаний: **пакет**, **сценарий**, **статья**.

- Карточка задаёт логическую идентичность знания.
- Техническая редакция описывает конкретный вариант этого знания.
- Перечень `protocolKeys` задаёт применимость редакции.
- Перевод содержит заголовок, пояснения и Markdown редакции.

Для пары **карточка / протокол** выбирается ноль или одна редакция. Одну редакцию
можно связать с несколькими протоколами при установленном совпадении описываемого
поведения. Применимость не наследуется от ветки, хроники, выпуска или соседнего номера.

Например, у одного пакета редакция 1 может поддерживать профили A и B, а редакция 2 — C.
Порядок `rev` не участвует в выборе: используется явная связь с выбранным профилем.
Изменение опкода или формата для отдельного контекста описывается соответствующей
редакцией. Исправление текста или добавление перевода само по себе новую редакцию
не создаёт. Изменение переиспользуемой редакции затрагивает все её протоколы.

Все статьи имеют явную применимость. Общий для многих протоколов материал получает
их перечень тем же способом, что пакет или сценарий.

### Содержание знаний

У пакета `server` и `direction` находятся в карточке. Опкод и состояния применения —
в технической редакции. Опкод представляет последовательность компонентов с типами
`u8`, `u16le`, `u32le`; значение и разрядность каждого компонента существенны.

Сценарии и статьи могут затрагивать Login, Game или оба сервера. Порядок сообщений,
условия, отказы, поля пакетов и механизмы обмена описываются в Markdown. Отдельная
машиночитаемая модель полей пакета или автомата сценария пока не утверждена.
Внутренний Login↔Game эмулятора не является третьим клиентским каналом справочника.

## Идентичность и версии

| Значение                       | Назначение                                                       |
| ------------------------------ | ---------------------------------------------------------------- |
| `id`                           | Постоянный UUID v4 записи; используется предметными SQL-ссылками |
| `code`                         | Устойчивое машинное обозначение именованной карточки или выпуска |
| `key`                          | Вычисляемый публичный адрес API                                  |
| `number`, `variant`            | Реальный игровой номер и наш различитель профиля                 |
| `rev`                          | Положительный номер технической редакции внутри карточки         |
| `revision()`                   | Полный SHA-256 содержимого базы для конкурентной записи          |
| `schema_rev` / `schemaVersion` | Совместимость SQL-структуры и предметного API                    |
| `dataVersion`                  | Явная метка набора данных; не заменяет хеш конкурентной ревизии  |
| `formatVersion`                | Версия файлового формата обмена                                  |

UUID общих записей и встроенных источников глобально уникальны и не зависят от языка.
Код карточки уникален внутри её вида; код выпуска — внутри хроники. Техническое имя
пакета `name` изменяемо и не является передаваемым по сети идентификатором.

Примеры адресов: `branch:main`, `chronicle:high-five`, `chronicle:high-five:base`,
`packet:key-packet`, `packet:key-packet:rev-1`. Обычные `put`/`update` сохраняют UUID
и составляющие адреса. SQL не хранит отдельные `key` или `slug`.
Имя файла экспорта — производное представление первичного ключа, а не новый ID.

## Языки, источники и неполнота

Одна техническая запись имеет независимые переводы из реестра `locales`.
Инициализация создаёт `ru` и `en`; другие языки добавляются данными. Язык документации
не является регионом клиента и не меняет техническую применимость.

Перевод содержит `title`, `summary`, `description`, `source`, `translationStatus`
и `openQuestions`. Источник имеет контракт `{ id, url, title, summary? }`, URL — HTTP(S).
Источник принадлежит одному переводу; повторяющиеся ссылки у разных владельцев
получают разные UUID. В `summary` можно указать, какое утверждение подтверждено.
Для кода фиксируется конкретный коммит и, когда возможно, строки.

Исследование эмулятора подтверждает его реализацию. Статус полноты и наличие ссылки
сами по себе не означают проверку официальным клиентом.

| Состояние                                     | Значение                                                         |
| --------------------------------------------- | ---------------------------------------------------------------- |
| `status: missing`                             | Знание заведено, описание может отсутствовать                    |
| `status: partial`                             | Исследование содержит полезные, но неполные сведения             |
| `status: documented`                          | Заявлена полнота описания в выбранном объёме                     |
| Перевода нет или `translationStatus: missing` | Текст нужного языка отсутствует                                  |
| `translationStatus: ready`                    | Перевод отмечен готовым                                          |
| `translationStatus: outdated`                 | Перевод отмечен требующим обновления                             |
| Пустая применимость                           | Поддерживаемые протоколы ещё не установлены                      |
| `opcode: null`                                | Опкод неизвестен; это отличается от известного нулевого значения |

Статусы задаются явно. База не определяет качество перевода и не помечает его
устаревшим автоматически. Точные условия проверки полноты — в
[контракте базы](database-contract.md#проверка-знаний).

Markdown хранится буквально. Директивы вроде `{{link packet:key-packet}}` относятся
к содержимому документа. Их разрешение по протоколу и языку — ответственность
потребителя, описанная в [сценариях чтения](user-journeys.md).
