# Пользовательские сценарии

Документ задаёт принятое поведение продукта. Операции базы реализованы;
интеграция потребителей и дев-редактор имеют статус, указанный в
[обзоре архитектуры](README.md#компоненты-и-ответственность).

## Чтение документации

Основной пользователь — разработчик. Он выбирает конкретный протокол и язык,
затем читает применимые пакеты, сценарии и статьи.

### 1. Выбрать протокол

Входами служат каталог протоколов, фильтры по ветке/хронике/выпуску и прямая ссылка.
Последовательный обход каталога не обязателен. В карточке протокола показываются
его номер, различающий контекст и известная принадлежность к выпускам.

Запрос по одному числу может иметь несколько результатов, если для него установлены
разные пакетные протоколы. Например, при наличии таких вариантов поиск `152`
должен позволить различить `152`, `152-rev-1`, `152-rev-2`. Это пример поведения,
а не перечень текущих записей. Точный ключ выбирает одну запись; приложение
не выбирает первый найденный профиль молча. Различие страны, ветки или выпуска
само по себе не создаёт вариант протокола.

Регион является справкой. Выбор Login/Game и направления пакетов уточняет раздел
внутри профиля и не создаёт другой протокол.

Основной каталог — компактная таблица выпусков и региональных протоколов в явном
порядке исходного Akumu. Дополнительные хроники отделены от основного ряда.
Номер открывает техническую документацию; название хроники — самостоятельную
страницу с описанием, выпусками, региональными датами, протоколами и источниками.
Неизвестные даты/страны показываются явно; региональный столбец не заполняется
по общему перечню регионов номера. Поиск не изменяет последовательность строк.

### 2. Найти материал

Потребитель запрашивает карточки или технические редакции с `protocolKey`.
Доступны фильтры вида знания, сервера и, для пакетов, направления.
Сценарий может переходить от Login к Game.

Ветки и выпуски показывают контекст выбранного протокола, но не определяют
применимость материалов. Список без профильного фильтра является каталогом
знаний для поиска или редактирования, а не готовой документацией протокола.

### 3. Выбрать редакцию и перевод

1. Для карточки и выбранного протокола найти применимую редакцию.
2. Получить из `translations` текст выбранного языка.
3. Показать Markdown, источники, полноту исследования и открытые вопросы.

Результаты различаются:

| Результат                             | Поведение потребителя                                      |
| ------------------------------------- | ---------------------------------------------------------- |
| Протокол или карточка не найдены      | Сообщить об отсутствии выбранной записи                    |
| Применимой редакции нет               | Показать отсутствие описания для этого протокола           |
| Редакция неполная                     | Показать доступные сведения вместе со статусом и вопросами |
| Перевода нет или он помечен `missing` | Явно показать отсутствие текста нужного языка              |
| Перевод помечен `outdated`            | Показать его состояние вместе с доступным текстом          |

Отсутствие применимости не доказывает, что пакет отсутствует у клиента.
Другой язык, соседний протокол и редакция с большим `rev` не используются как fallback.

### 4. Прочитать Markdown и перейти по ссылкам

Рендер документации выполняется в контексте выбранных протокола и языка.
Внутренняя ссылка на логическую карточку сохраняет этот контекст и разрешается
через её применимую редакцию. Внешние ссылки ведут к источникам непосредственно.

Каталоговые ссылки самодостаточны и не выбирают техническую редакцию:
`{{link branch:main}}`, `{{link saga:the-chaotic-throne}}`,
`{{link chronicle:the-kamael}}`, `{{link release:the-kamael}}`, `{{link region:na}}`
и `{{link protocol:273}}`. Код релиза не содержит код хроники и не меняется при
перегруппировке. Каталоговые записи поддерживают `link`, но не технические `include`/`value`.

Core предоставляет `referenceMarkdownDirectives` и `renderReferenceMarkdown`;
прежний рендерер знаний сохраняет свой контракт. Веб разрешает хронику в её страницу,
релиз — в его раздел страницы текущей хроники, протокол — в точный профиль.
Отдельные страницы остальных групп и регионов пока не реализованы: вместо ссылок на
несуществующие URL отображается явная диагностика недоступной ссылки.

База возвращает текст без обработки директив. Выбор редакции, обработка ссылок
и вставок относятся к представлению; URL страниц задаёт приложение. Проверка
графа вставок и диагностика неразрешённых ссылок также выполняются потребителем.

## Наполнение агентом

Основной способ пополнения — исследовательский агент, читающий код серверных
реализаций и другие источники. Рабочая запись выполняется через предметный
CLI `apps/cli` (`pnpm cli`). Технический мини-CLI пакета базы также использует тот же API.

1. Найти или создать нужные профили и вспомогательные записи каталога.
2. Установить, какую предметную часть описывает источник и для каких протоколов.
3. Выбрать карточку и подходящую техническую редакцию либо создать новую.
4. Подготовить Markdown, переводы, источники и открытые вопросы.
5. Выполнить предметные команды либо передать связанные изменения одним `batch`
   с явным списком `protocolKeys`.
6. После успешной записи экспортировать снимок для Git.

Неполный результат допустим. Агент не переносит сведения из соседней ревизии
ради заполнения обязательных полей. Если найден иной технический вариант,
применимость изменяется только для установленных контекстов.

Перевод добавляется к существующей общей записи командой `translate`: пакет, опкод,
связи с протоколами и другие языки сохраняются. В низкоуровневом `patch` перечни,
включая `translations`, заменяются целиком. `ifRevision` защищает пакет от записи
поверх изменившейся базы; при конфликте требуется новое чтение. `--dry-run`
позволяет проверить результат без сохранения, обычная запись показывает действие,
ключи и затронутые поля. Пользователь видит предметное намерение команды.

## Дев-редактор Markdown

Предусмотрен интерфейс редактирования текстов в режиме разработки. Он должен
загружать выбранный перевод, редактировать Markdown и сохранять результат через
тот же CLI с проверкой ревизии. Это принятое направление, ещё не реализованный
интерфейс. Редактируемый файл или буфер является представлением текста; рабочим
хранилищем остаётся SQLite.

Точные правила чтения и записи: [контракт базы](database-contract.md).
Сохранение результатов в Git: [обмен данными](data-exchange.md).
