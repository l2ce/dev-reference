# Контракт базы данных

Здесь описано поведение `packages/database`. Команды запуска находятся в
[руководстве пакета](../../packages/database/README.md), физические ограничения —
в [матрице таблиц](table-matrix.md).

## Доступ к SQLite

Drizzle описывает схему и выполняет все предметные SELECT/INSERT/DELETE: чтение
карточек и переводов, разрешение связей, фильтры, COUNT/LIMIT и сохранение записей.
Типы SQL-строк выводятся из деклараций таблиц. Реестр коллекций сохраняет соответствие
вида записи конкретной таблице; универсального `Record<string, unknown>` вместо
предметных SQL-типов в этом слое нет.

SQL-выражения внутри Query Builder применяются для вычисляемых ключей, CASE,
конкатенации и поиска Unicode. Они используют типизированные колонки и параметры
Drizzle. Пользовательские значения не соединяются с текстом запроса.

Нативный `better-sqlite3` обслуживает `sqlite_schema`, `PRAGMA`, DDL-восстановление,
проверку FK и динамический обмен физическими таблицами. Эти операции намеренно
работают с фактической структурой файла. Владельцем транзакции остаётся сценарий
API или импорта; Drizzle использует тот же физический client внутри этой транзакции.

Zod проверяет входные документы и итоговые DTO, предметный валидатор — смысл связей.
Типизация Query Builder дополняет эти проверки, а не заменяет проверку внешних данных.

## Представление записи

Предметный API использует оболочку:

```text
{ collection, key, kind, value }
```

- `collection` определяет схему содержимого.
- `key` — вычисляемый публичный адрес, совпадающий с `value.key` и его предметными полями.
- `kind: entity` — карточка, протокол или выпуск; `implementation` — техническая редакция.
- `value.id` — постоянный UUID; язык не входит в адрес.

Коллекции: `branches`, `chronicles`, `chronicle-releases`, `protocols`, `packets`,
`scenarios`, `articles`, `packet-revisions`, `scenario-revisions`, `article-revisions`.
Это представления API: физические имена таблиц и колонки перечислены отдельно.

У каталога и редакций знаний переводы вложены в `translations`. В карточках пакетов,
сценариев и статей текст находится через редакции. В переводе список источников
называется `source`, в SQLite — `sources_json`. `order` соответствует `sort_order`.
Предметные ссылки API используют ключи, SQL-ссылки — UUID.

Схемы нормализуют значения по умолчанию: отсутствующий список — `[]`, `order` —
`null`, опкод — `null`, `variant` — `0`, `status` — `missing`. Переводы сортируются
по locale. Текст Markdown и значимый порядок остальных списков сохраняются.

## Чтение

| Операция                           | Результат                                                            |
| ---------------------------------- | -------------------------------------------------------------------- |
| `manifest()`                       | Версия схемы, версия данных и реестр языков; `null` до инициализации |
| `get({ collection, key })`         | Карточка или выпуск; `undefined`, если запись не найдена             |
| `getRevision({ collection, key })` | Конкретная техническая редакция; `undefined`, если её нет            |
| `list(query)`                      | `{ items, total }` с SQL-пагинацией                                  |
| `snapshot()`                       | Полный согласованный предметный снимок, включая все переводы         |
| `revision()`                       | SHA-256 полного предметного снимка                                   |

`getImplementation` — совместимое имя `getRevision`. Методы чтения редакции не
проверяют, выбрал ли вызывающий код протокол: соблюдение профильного контекста
при рендере относится к [потребителю](user-journeys.md).

### Фильтры list

| Фильтр                      | Допустимые коллекции                                |
| --------------------------- | --------------------------------------------------- |
| `branchKey`                 | `chronicles`                                        |
| `ownerKey`                  | `chronicle-releases` и три коллекции редакций       |
| `chronicleReleaseKey`       | `protocols`                                         |
| `protocolKey`               | Карточки знаний, их редакции и `chronicle-releases` |
| `server`                    | Карточки знаний и их редакции                       |
| `direction`                 | `packets`, `packet-revisions`                       |
| `search`, `limit`, `offset` | Все предметные коллекции                            |

Условия объединяются и применяются до COUNT/LIMIT. Неподходящие комбинации
отклоняются. Фильтр по отсутствующей связанной записи возвращает пустой список.
`limit`: 1–1000, по умолчанию 50; `offset`: от 0, по умолчанию 0.
Порядок результата — по публичному ключу, а не по хронологии или `sort_order`.

Поиск проверяет ключ, техническое имя пакета и заголовки/аннотации собственных
переводов запрошенной коллекции. Используются NFKC и приведение к нижнему регистру.
Поиск по карточке пакета не ищет автоматически в текстах её редакций.
Языкового фильтра нет: возвращаются все имеющиеся переводы, без подстановки отсутствующих.

Каждый составной вызов удерживает одну читающую транзакцию. Последовательные
самостоятельные вызовы могут увидеть разные состояния; полный `snapshot()` нужен,
когда потребителю требуется одно основание для нескольких связанных действий.

## Запись

`applyChanges` и CLI `apply` принимают пакет операций:

| Операция | Предусловие и эффект                                                      |
| -------- | ------------------------------------------------------------------------- |
| `create` | Адрес отсутствует; создаётся полная запись                                |
| `put`    | Создаётся отсутствующая запись либо полностью заменяется существующая     |
| `update` | Запись существует; переданные поля заменяются на верхнем уровне           |
| `delete` | Запись существует; удаляется вместе с принадлежащими ей редакциями знаний |

UUID и составляющие публичного адреса существующей записи сохраняются.
Массивы и вложенные объекты в `patch` заменяются целиком. Ссылки проверяются в
конечном состоянии пакета: карточку и редакцию можно передать в любом порядке.
Повторные операции над одним адресом и операции над редакцией одновременно
с удалением её карточки отклоняются.

Удаление карточки знания каскадно удаляет её редакции, переводы и применимость.
Удаление ветки, хроники или протокола требует явно устранить остающиеся ссылки;
например, удаление хроники не удаляет её выпуски автоматически.
`replaceSnapshot` заменяет всю базу, включая реестр языков и метаданные. Это отдельная
операция полного восстановления, не эквивалент обычного `put`.

### Транзакция и конкурентность

1. Начать IMMEDIATE-транзакцию и прочитать общий снимок.
2. Сравнить переданный `ifRevision` с текущей ревизией всей базы.
3. Рассчитать конечные записи и проверить их целиком.
4. При изменениях сохранить снимок и зафиксировать транзакцию.

`ifRevision` необязателен; при его несовпадении возникает `REVISION_CONFLICT`.
Проверка выполняется и для no-op. Изменение любого перевода меняет общую ревизию.
Результат содержит `changed` — число изменённых адресов, включая каскадные удаления,
и `revision` — новый хеш. No-op возвращает `changed: 0` и не переписывает строки.

Опция `dryRun` выполняет те же проверки и расчёт, но пропускает сохранение строк.
В этом режиме возвращаемая ревизия описывает рассчитанный результат, а не текущее
состояние на диске. CLI отдельно показывает `previousRevision` и признак `dryRun`.

Хеш ревизии вычисляется по всему предметному снимку: записи сортируются по ключу,
ключи JSON-объектов — детерминированно. Порядок значимых списков и содержание строк
влияют на хеш. Это 64-символьный SHA-256, независимый от коротких имён файлов экспорта.

Текущая реализация записи материализует и при изменениях пересохраняет полный
предметный снимок. Это не построчный UPDATE и не обещание стоимости, пропорциональной
только размеру пакета. SQLite-соединения используют WAL; владельцы API закрывают
свои соединения через `close()`.

При предметной записи очищаются и заполняются только объявленные таблицы пакета.
Полный импорт отдельно приводит структуру файла к текущей схеме.

## Проверка знаний

SQL проверяет типы, PK, FK, UNIQUE и CHECK. Валидатор дополнительно проверяет:

- UUID v4 в нижнем регистре и глобальную уникальность UUID записей и источников;
- соответствие ключа записи её типу, коду, владельцу и номеру редакции;
- существование предметных ссылок и отсутствие повторов в значимых списках;
- зарегистрированные языки и единственный перевод владельца на язык;
- не более одной редакции карточки на протокол;
- разрядность и коллизии опкодов.

Для `partial` и `documented` требуется источник хотя бы в одном переводе записи.
Для `documented` дополнительно требуется непустой Markdown хотя бы на одном языке;
у редакции пакета — известный опкод. Полнота не доказывается количеством источников.

Коллизия опкодов проверяется для совпадающих протокола, сервера, направления и
полной последовательности компонентов. Состояния конфликтуют при пересечении;
пустой список означает отсутствие установленного ограничения и считается
пересекающимся с любым другим. Markdown-директивы этим валидатором не разбираются.

## Инициализация и совместимость

Обычное открытие отсутствующего файла создаёт текущую SQL-структуру. CLI `init`
добавляет метаданные и языки `ru`, `en`; повторная инициализация отклоняется.
До появления метаданных полный снимок и предметная запись недоступны.
Read-only открытие не создаёт отсутствующий файл.

Несовместимая схема при обычном открытии даёт `SCHEMA_MISMATCH`. Импорт может
пересоздать её текущим DDL и восстановить данные одной транзакцией.
Проверка совместимости учитывает явные индексы, включая индексы уникальности.
История пошаговых SQL-миграций не ведётся; входной снимок должен соответствовать
поддерживаемому контракту. Правила импорта — в [описании обмена](data-exchange.md).
