# Обмен данными

SQLite хранит рабочие предметные данные. Экспорт сохраняет полный снимок таблиц
в `packages/database/data/` для Git; импорт восстанавливает из него рабочую базу.
Оба направления принадлежат `packages/database` и доступны через его CLI.

## Формат снимка

Основной формат — **`sqlite-tables`, версия 1**. Каждая пользовательская таблица
получает папку, каждая строка — JSON-файл. Перечень таблиц, колонок, первичных
ключей и объёмов извлекается из SQLite динамически. Внутренние `sqlite_*` исключаются.

```text
data/
  manifest.json
  protocols/<uuid>.json
  packet_protocols/5b401a1c.json
  packet_revision_translations/9e2a7b10.json
  locales/ru.json
  metadata/1.json
```

Корневой манифест имеет вид:

```text
{ format: "sqlite-tables", formatVersion: 1,
  tables: [{ name, columns, primaryKey, rows }, ...] }
```

Он описывает состав снимка, а не полный DDL. Типы, FK и ограничения берутся из
текущей схемы пакета. `metadata.schema_rev` задаёт совместимость предметной структуры
независимо от `formatVersion`. Числовые ревизии протоколов и знаний имеют другой смысл.

В файл строки попадают физические колонки и значения, включая служебные таблицы
и таблицы связей. Вычисляемые ключи и объединённые документы API в этот формат
не добавляются. Представление значений:

| SQLite                                       | JSON                                                                      |
| -------------------------------------------- | ------------------------------------------------------------------------- |
| TEXT                                         | Строка без изменения содержимого, в том числе Markdown и JSON внутри TEXT |
| Безопасное целое / REAL                      | Число                                                                     |
| INTEGER вне безопасного диапазона JavaScript | `{ "$integer": "..." }`                                                   |
| BLOB                                         | `{ "$blob": "<base64>" }`                                                 |
| NULL                                         | `null`                                                                    |

Пустые таблицы включаются в манифест и получают папки при экспорте. После Git
checkout пустая папка может отсутствовать: `rows: 0` сохраняет её смысл.

## Имена файлов

1. Для одиночного строкового или числового PK используется его значение, если
   оно подходит под `[a-zA-Z0-9][a-zA-Z0-9_.-]{0,149}`.
2. Для составного или неподходящего одиночного PK берётся массив его экспортируемых
   значений в порядке колонок первичного ключа. Вычисляется SHA-256 от
   `JSON.stringify` этого массива, имя — первые **8 строчных hex-символов** и `.json`.

Префикса `key-` у новых хешированных имён нет. Типы и порядок компонентов существенны.
Изменение поля вне PK или добавление другой записи не меняет имя. Изменение самого
PK может изменить имя; UUID предметной сущности и файловый адрес — разные понятия.

До создания файлов проверяются имена всех строк внутри каждой таблицы, включая
возможное совпадение хеша с читаемым одиночным ключом. При коллизии возникает
`EXPORT_FILENAME_COLLISION` с путём и обоими полными PK. Экспорт останавливается;
автоматического удлинения или перенумерации нет. Одинаковые имена в разных папках
таблиц допустимы. Повтор полного PK отдельно отклоняется как `INVALID_TABLE_KEY`.

Импорт принимает также прежние имена `key-<полный SHA-256>.json`, проверяя их
соответствие строке. Следующий экспорт сохраняет такие строки под короткими именами.

## Импорт

1. Проверить манифест, набор файлов, имена, количество строк и состав колонок.
2. Восстановить снимок в SQLite в памяти на текущем DDL.
3. Проверить совпадение таблиц, колонок и PK, затем SQL-ограничения и предметную модель.
4. Открыть целевой файл и в одной IMMEDIATE-транзакции подготовить текущую схему,
   заменить все строки и повторно проверить FK и предметные правила.
5. Зафиксировать результат и сообщить об успешном завершении.

Импорт — **полная замена**, без неявного слияния с локальными изменениями.
Входной SQL не исполняется. Порядок таблиц не задаёт порядок разрешения ссылок:
при восстановлении FK временно отключаются и проверяются до COMMIT, после чего
обычный режим FK восстанавливается. Ошибка до COMMIT откатывает структуру и данные.

Дополнительная таблица может быть обнаружена и экспортирована, но её импорт
требует соответствующей схемы пакета. Динамический экспорт не является загрузчиком
произвольного SQLite DDL. Автоматического объединения самостоятельных языковых
записей прежней модели по совпадающим ключам нет.

Поддерживается вспомогательный документный импорт текущей схемы:
`collection/UUID.json` с манифестом `schemaVersion`, `dataVersion`, `defaultLocale`,
`locales`. Он использует предметные записи API, а не физические строки. Основной
экспорт всегда остаётся табличным.

## Экспорт и публикация

1. В одной читающей транзакции получить физические строки и проверить FK и модель.
2. Проверить однозначность будущих имён файлов.
3. Получить эксклюзивную блокировку каталога назначения.
4. Записать полный снимок во временный соседний каталог.
5. Перенести предыдущий экспорт в резервный каталог и установить подготовленный.
6. Удалить резервный каталог и снять блокировку.

Изменения SQLite после чтения не смешиваются с подготовленным снимком.
Назначение должно быть пустым либо содержать полный распознаваемый экспорт.
Рабочий SQLite-файл внутри назначения запрещён. Строки создаются с эксклюзивным
открытием файла; существующий файл в staging не перезаписывается.

Штатная ошибка записи сохраняет прежний экспорт. Публикация использует два
переименования: аварийное завершение между ними может потребовать восстановления
из резервного каталога. Это не единая транзакция SQLite и файловой системы.
Ошибка очистки после публикации или наблюдателя после COMMIT помечается
`committed: true`: результат уже сохранён. Значение прогресса 100% относится
к завершённой фиксации, а не к последнему подготовленному файлу.

## Воспроизводимость

При неизменных строках и схеме повторный экспорт даёт одинаковые имена и содержимое
файлов. Для канонического снимка цикл экспорт → импорт → экспорт сохраняет файлы
побайтово. Равенство относится к данным, UUID, связям, порядку списков и текстам,
а не к байтам самого SQLite-файла.
